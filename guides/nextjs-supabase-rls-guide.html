DATABASE SECURITY · RLS

바이브코딩 최다 사고 1위:
Supabase · Firebase DB 공개 노출 막는 보안 규칙

Lovable, Bolt, Cursor로 만든 SaaS MVP가 런칭 첫날 해킹당하는 가장 흔한 원인은 서버 취약점이 아니라 RLS(Row Level Security)가 꺼진 Supabase 테이블과 전체 개방된 Firestore 규칙입니다.

UPDATED 2026-11-25READ TIME: 4 MINSUPABASE RLS · FIRESTORE RULES

1. 왜 브라우저 Anon Key만으로 전체 회원 DB가 털릴까?

Supabase의 NEXT_PUBLIC_SUPABASE_ANON_KEY나 Firebase의 apiKey는 브라우저에서 호출하도록 설계된 공개 키입니다. 문제는 RLS를 켜지 않으면 누구나 개발자 도구에서 해당 공개 키를 복사해 GET /rest/v1/users?select=* 요청 한 번으로 모든 사용자의 이메일·결제 기록을 조회하고 심지어 DELETE까지 실행할 수 있다는 점입니다.

2. Supabase RLS 1분 잠금 SQL 패턴 (복사해서 바로 적용)

모든 사용자 데이터 테이블에 아래 SQL을 실행해 기본 접근을 차단하고, 본인 소유 행만 읽고 쓰도록 제한하세요.

-- 1) 테이블에 Row Level Security 강제 활성화
ALTER TABLE public.profiles ENABLE ROW LEVEL SECURITY;

-- 2) 본인 데이터만 조회(SELECT) 허용
CREATE POLICY "Users can view own profile"
ON public.profiles FOR SELECT
USING (auth.uid() = user_id);

-- 3) 본인 데이터만 생성/수정(INSERT/UPDATE) 허용
CREATE POLICY "Users can insert own profile"
ON public.profiles FOR INSERT
WITH CHECK (auth.uid() = user_id);

CREATE POLICY "Users can update own profile"
ON public.profiles FOR UPDATE
USING (auth.uid() = user_id)
WITH CHECK (auth.uid() = user_id);

3. Firebase Firestore 안전 규칙 (테스트 모드 즉시 종료)

allow read, write: if true; 상태로 배포된 프로젝트는 반드시 아래처럼 로그인 사용자 본인 문서로 스코프를 좁혀야 합니다.

rules_version = '2';
service cloud.firestore {
  match /databases/{database}/documents {
    match /users/{uid}/{document=**} {
      allow read, write: if request.auth != null && request.auth.uid == uid;
    }
    match /{document=**} {
      allow read, write: if false;
    }
  }
}

4. 절대 실수하면 안 되는 Service Role Key

Supabase의 service_role 키는 모든 RLS를 우회하는 마스터 키입니다. 절대로 클라이언트 코드, GitHub 커밋, NEXT_PUBLIC_ 환경변수에 넣지 말고 오직 서버리스 백엔드 환경변수에만 보관하세요.
